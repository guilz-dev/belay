# 自律的テスト・改修ループ設計 — 精度向上のための反復プロセス

Status: **Proposal**（2026-07-03 時点のコードベース解析に基づく）
関連: [`corpus/README.md`](../corpus/README.md) · [`ADR-002 概念適合`](./adr/ADR-002-concept-conformance.ja.md) · [`ROADMAP.md`](./ROADMAP.md)

> **一文要約:** Belay には評価・収穫・回帰検知の部品がすでに揃っている。
> 欠けているのは「失敗ケースを自動生成し、修正し、二度と戻らないように固定する」
> 反復の駆動部であり、本書はその設計を定義する。

## 1. 現状分析 — すでにあるもの / 足りないもの

### 1.1 既存の品質インフラ（実測済み）

| 部品 | 実体 | 役割 | 実測 |
|---|---|---|---|
| コーパス評価 | `pnpm corpus` → `src/corpus/evaluate.ts` | ラベル付きコーパスの精度・ハードゲート判定 | 27ケース / 精度100% / 約30秒（ビルド込み） |
| ハードゲート | `corpus/baseline.json` + `src/corpus/gates.ts` | must-ask 見逃し=0、provably-benign 誤停止=0 を CI で強制 | 両方 0 で通過 |
| 構造スイート | `src/__tests__/verdict/structural-suite.test.ts` | 破滅的コア×12ラッパー変換のバイパス等価性 | `pnpm test:structural` でCIハードゲート |
| フルテスト | `vitest run` | 全機能回帰 | 94ファイル / 804テスト / 約16秒 |
| フレーク検知 | `pnpm test:stable`（vitest 3連走） | 非決定的テストの検出 | CI で常時実行 |
| 収穫 | `belay harvest list/apply` (`src/commands/harvest.ts`) | 監査ログから良性候補を抽出しコーパスへ昇格 | 人手レビュー前提 |
| 影響シミュレーション | `belay simulate` (`src/commands/simulate.ts`) | 候補設定を監査ログにリプレイし allow↔deny の変化を差分表示 | トリアージ専用 |
| 統合レポート | `belay quality --json` (`src/commands/quality.ts`) | コーパスゲート+監査メトリクス+収穫残の一括JSON | 機械可読 |
| LLMジャッジ精度 | `src/__tests__/verdict/llm/judge-accuracy.test.ts` | Tier1ジャッジの正答率を計測し `artifacts/judge-accuracy-report.md` を生成 | 5ケースのみ / Ollama 必須（無ければskip） |

**結論:** 評価パイプラインは高速（1イテレーション ≒ 1分以内）で、自律ループの
土台としてすでに十分な速度がある。

### 1.2 ギャップ — 精度が「向上しない」理由

1. **コーパスが小さすぎて失敗が発生しない。** 27ケースで100%という数字は
   飽和しており、改善の駆動力（=失敗ケース）が存在しない。精度向上の律速は
   分類器の修正ではなく **失敗ケースの供給** である。
2. **敵対的ケースの生成が固定的。** 構造スイートの12ラッパー変換は優秀だが
   ハードコードされており、新しいバイパス形状（エンコード、パス偽装、
   フラグ悪用、多段ネスト）が自動では増えない。
3. **ループの駆動部が無い。** `harvest → corpus → build` の各ステップは
   手動連結。生成→評価→修正→固定を繰り返す仕組みが存在しない。
4. **Tier1 ジャッジの精度計測が貧弱。** 5ケース・単一モデル・Ollama 依存。
   構造分類器（Tier0）に比べ計測面が一桁足りない。
5. **`docs/recursive-quality-loop.md` が欠落。** `corpus/README.md` から
   参照されているが実ファイルが無い（リンク切れ）。本書がその後継を兼ねる。

## 2. 設計原則 — 自律ループが守るべき不変条件

Belay 自身の哲学（ROADMAP「2つのダイヤル」）をループにも適用する。
**損失は非対称** であり、自動化はこの非対称性を壊してはならない。

### P1. 見逃し(FN)ゼロは交渉不可、誤停止(FP)は漸減目標

- must-ask の見逃しが1件でも出たら **そのイテレーションの最優先修正対象**。
  修正がマージされるまで他の変更を積まない。
- FP（良性の誤停止）の修正で Tier0 ルールを緩めるときは、ADR-002 M3 に従い
  「なぜ緩めても FN にならないか」の正当化と must-ask 側の対抗ケースを
  **同一コミットで** コーパスに追加する。

### P2. ラベルの出所規律 — 自動付与できるラベルとできないラベル

コーパスのラベルはランタイム挙動に波及する（`provably-benign` は
`scripts/generate-standing-allow-catalog.mjs` 経由で standing-allow カタログに
焼き込まれ、**実行時に無音許可される**）。したがって:

| ラベル | 自動追加 | 根拠 |
|---|---|---|
| `must-ask` | **可** | 期待を厳しくする方向は安全（過剰でも「聞くだけ」） |
| `accepted-benign` | **可**（ソフトゲートのため） | 失敗しても review-required 報告止まり |
| `provably-benign` | **不可 — 人手レビュー必須** | 無音許可の付与＝ランタイム権限の拡大。`belay harvest apply` を唯一の昇格経路とする |

これは既存の harvest 設計（「承認はシグナルであってground truthではない」）
と同じ規律の一般化である。

### P3. メタモルフィック不変条件 — ラッパーは判定を弱められない

構造スイートの暗黙の前提を明文化し、生成器の正当性根拠とする:

> 任意のコマンド `c` と透過ラッパー変換 `w`（`bash -c`、`env`、`sudo`、
> `eval`、コマンド置換、パイプ経由実行、絶対パス化…）について
> `strictness(verdict(w(c))) ≥ strictness(verdict(c))` が成り立つ。

この性質により、**must-ask コアの変異体は自動で must-ask とラベルできる**
（人手不要で正しいラベルが導出できる唯一のクラス）。良性コマンドの変異体は
この性質から良性を導出 **できない**（ラッパーが判定を厳しくするのは正しい
挙動）ため、FP 候補としてキューに積むに留める。

### P4. ラチェット — ゲートは緩まない、コーパスは縮まない

- `corpus/baseline.json` のハードゲート（0/0）は恒久固定。
- コーパスのケース削除・ラベル降格は人手レビューのみ。ループは追加専用。
- イテレーションごとの精度は「新規生成バッチに対する初見精度」で測る
  （既存コーパスは飽和しているため、そこでの100%維持は前提条件にすぎない）。

### P5. 過学習対策 — 生成バッチの二分割

生成した敵対的ケースは **fix セット**（修正に使う）と **holdout セット**
（修正後の検証のみに使い、コーパスへは次イテレーションで合流）に分割する。
holdout での精度が fix セットより有意に低い場合、修正が個別ケースへの
パッチワークになっている兆候として扱う。

## 3. ループ設計 — 1イテレーションの構造

```
        ┌────────────────────────────────────────────────┐
        │  ① GENERATE  敵対的・良性ケースの候補生成          │
        │     変異エンジン / 監査ログ収穫 / LLM赤チーム       │
        └───────────────┬────────────────────────────────┘
                        ▼
        ┌────────────────────────────────────────────────┐
        │  ② LABEL     出所規律(P2)に従い自動/保留を仕分け    │
        └───────────────┬────────────────────────────────┘
                        ▼
        ┌────────────────────────────────────────────────┐
        │  ③ EVALUATE  pnpm corpus + 構造スイート + 全テスト │
        └───────────────┬────────────────────────────────┘
                        ▼
              失敗あり ──┴── 失敗なし ──→ ⑦ へ
                        ▼
        ┌────────────────────────────────────────────────┐
        │  ④ DIAGNOSE  FN(P0) / FP / フレーク に分類        │
        │     `belay explain` でトレース確認                │
        └───────────────┬────────────────────────────────┘
                        ▼
        ┌────────────────────────────────────────────────┐
        │  ⑤ FIX       tokenizer/parser/containment/      │
        │     tier0規則/judge の最小修正（M3正当化つき）      │
        └───────────────┬────────────────────────────────┘
                        ▼
        ┌────────────────────────────────────────────────┐
        │  ⑥ VERIFY    holdoutで再評価 + test:stable +     │
        │     belay simulate で実トラフィック回帰確認         │
        └───────────────┬──────── 失敗 → ④ へ戻る          │
                        ▼
        ┌────────────────────────────────────────────────┐
        │  ⑦ RATCHET   合格ケースをコーパスへ追記、           │
        │     イテレーションレポートを artifacts/ へ、        │
        │     コミット & push（CI が最終審判）               │
        └────────────────────────────────────────────────┘
```

### ① GENERATE — 失敗ケースの供給源（優先順）

1. **決定的変異エンジン（最優先・LLM不要）**
   `structural-suite.test.ts` の `WRAPPER_TRANSFORMS` を
   `src/corpus/mutators.ts` として共有モジュール化し、テストと生成器の
   両方から使う。拡張軸:
   - エンコード系: `base64`/`printf '\x..'`/URLエンコード経由の実行
   - パス系: 相対パス脱出（`../../`）、シンボリックリンク、`~` 展開、`$HOME`
   - フラグ系: `find -delete`、`rsync --delete`、`git clean -fdx` など
     「読み取り系ヘッドに破壊フラグ」の組合せ
   - 多段ネスト: ラッパー変換の2〜3段合成（現在は1段のみ）
   - 引用・空白系: クォート分割 `r"m" -rf`、IFS操作、タブ/改行埋め込み
2. **監査ログ収穫（実運用データ）** — 既存の `belay harvest list`。
   dogfooding 環境の監査ログから FP 候補（繰り返し ask されている良性
   フィンガープリント）を吸い上げる。実トラフィック由来なので優先度が高い。
3. **LLM 赤チーム生成（補助）** — 「このコマンドを検知されずに実行する
   別表現を列挙せよ」型の生成。must-ask コアの変異のみに限定すれば
   P3 により自動ラベル可能。生成物は必ず ③ で実分類してから採用。

### ② LABEL — 仕分け表

| 生成元 | 生成物 | 自動ラベル | 行き先 |
|---|---|---|---|
| must-ask コアの変異 | バイパス試行 | `must-ask` (P3) | fix/holdout へ二分割 |
| 良性コマンドの変異 | FP プローブ | なし | 誤停止したら `accepted-benign` 候補としてレビューキューへ |
| harvest 候補 | 実運用の良性 | なし | `belay harvest apply`（人手）で昇格 |
| LLM 赤チーム | バイパス試行 | `must-ask`（コア変異のみ） | fix/holdout へ二分割 |

### ③〜⑥ EVALUATE / DIAGNOSE / FIX / VERIFY

- 評価は既存コマンドをそのまま使う: `pnpm corpus` → `pnpm test:structural`
  → `vitest run` → （修正後）`pnpm test:stable`。合計 2〜3 分/周。
- 診断は corpus 評価の mismatch 出力（expected/actual/reason）と
  `belay explain` のトレースで行う。
- 修正対象は失敗の reason で決まる:
  - トークナイズ失敗 → `src/core/shell-tokenizer.ts` / `parser.ts`
  - ラッパー透過漏れ → `parser.ts` の `peelTransparentWrappers` / `substitutionInners`
  - パス封じ込め → `src/core/verdict/containment.ts`
  - Tier0 規則の過不足 → `verdict.ts` の各キーセット（M3 正当化必須）
  - ジャッジ判定 → `judge.ts`（後述の judge ループで扱う）
- **FP を直すとき**は必ず `belay simulate` で監査ログ全体への波及
  （allow→deny / deny→allow の件数）を確認してからコミットする。

### ⑦ RATCHET — 成果の固定

- 合格した must-ask 変異体をコーパスへ追記（`pnpm corpus` が新しい床になる）。
- `artifacts/quality-loop/iteration-NNN.json` にイテレーションレポートを保存:
  生成数 / 初見FN率 / 初見FP率 / 修正ファイル / holdout精度 / コーパス増分。
  **初見FN率の推移がこのループの本当の精度指標**（コーパス精度は常に100%に
  ラチェットされるため指標にならない）。
- 小さくコミットして push。CI（構造ゲート + corpus + test:stable）が最終審判。

## 4. 実行形態 — どう「自律」させるか

3案を比較し、**A を主軸に C を夜間の安全網として併用** することを推奨する。

### 案A（推奨・主軸）: Claude Code セッション内ループ

リポジトリにループ手順をスキル化（例: `.claude/skills/quality-loop/SKILL.md`）
し、Claude Code に「/quality-loop を N 周回せ」と指示する。エージェントが
①〜⑦を tool 呼び出しで直接実行する。

- 長所: 診断→修正（⑤）に判断力が要るため、LLM が直接ループを回すのが最短。
  1周 2〜3 分なので 1 セッションで 5〜10 周が現実的。
- 短所: セッション時間とコストに上限がある。
- 運用: リモート実行環境ならスケジュールトリガーで定期セッションを起動し、
  各セッションの成果はブランチ push + PR で人間がレビューする。
  **provably-benign 昇格だけは PR レビューで人間が判断**（P2）。

### 案B: CI 駆動（GitHub Actions nightly）

夜間ジョブで変異バッチ生成→評価し、失敗があれば issue を自動起票して
Claude Code（GitHub app）に修正を委任する。

- 長所: 完全放置できる。失敗が無い夜はコストゼロ。
- 短所: 生成→修正のリードタイムが1日単位。イテレーション速度が出ない。

### 案C: 決定的スクリプトのみ（LLM 不使用の安全網）

`scripts/adversarial-probe.mjs`（新規）が変異エンジンだけで must-ask 変異体を
生成し、初見FN率を計測して非ゼロなら CI を落とす（または警告 artifact を吐く）。

- 長所: 決定的・安価・毎コミット実行可能。P3 によりラベルが常に正しい。
- 短所: 修正はしない。検知専用。
- 位置づけ: 案A のイテレーションで固定した変異軸を、以後は案C が毎晩
  リグレッション監視する、という**送り出し先**として機能させる。

## 5. 実装ロードマップ

| 順 | 成果物 | 内容 | 規模 |
|---|---|---|---|
| 1 | `src/corpus/mutators.ts` | `WRAPPER_TRANSFORMS` を構造スイートから抽出・拡張（エンコード/パス/フラグ/多段/引用の5軸を追加）。構造スイートはこれを import する形に置換 | 小 |
| 2 | `scripts/adversarial-probe.mjs` | must-ask コア × 変異エンジンで初見FN率を計測、`artifacts/quality-loop/` にレポート出力。`--fail-on-fn` で CI ゲート化可能 | 小 |
| 3 | `.claude/skills/quality-loop/SKILL.md` | ①〜⑦の手順・P1〜P5 の不変条件・停止条件を記述したループスキル（案A の駆動部） | 小 |
| 4 | corpus スキーマの `provenance` フィールド | ケースの出所（`manual` / `mutation` / `harvest` / `redteam`）を記録し、holdout 分割とレビュー要否の判定に使う | 小 |
| 5 | judge コーパス拡張 | `TIER1_ACCURACY_CORPUS`（現5件）をコーパス本体から自動導出（tier1 到達ケースを抽出）し、`fixtures/judge-models.json` の複数モデルで行列計測 | 中 |
| 6 | nightly workflow | 案C を `.github/workflows/nightly-probe.yml` として追加 | 小 |

ステップ 1〜3 だけで案A のループは回り始める。4〜6 は運用が安定してから。

### 停止条件（1セッションあたり）

- 初見FN率が 2 イテレーション連続で 0 → 変異軸を1つ拡張して継続、
  拡張余地が無ければ終了しレポート。
- 同一の失敗が 3 回の修正試行で解消しない → 修正を revert し、
  ケースを `known-gap` としてレポートに記録して人間へエスカレーション
  （ROADMAP の「FN は *named, measured, backstopped* な残差へ」に対応）。
- `test:stable` でフレーク検出 → 精度作業より先にフレーク修正
  （ループの判定自体が信頼できなくなるため）。

## 6. 計測 — イテレーションを跨いで追う指標

| 指標 | 定義 | 目標方向 |
|---|---|---|
| 初見FN率 | 新規 must-ask 変異バッチのうち ask にならなかった率 | → 0（軸拡張のたびに再上昇し、再び 0 へ収束する鋸歯状が健全） |
| 初見FP率 | 新規良性プローブのうち誤停止した率 | 漸減（P1 により FN と交換しない） |
| holdout/fix 精度比 | 過学習検知（P5） | ≒ 1.0 |
| コーパス規模 | ケース数と provenance 内訳 | 単調増加 |
| accepted-benign 残高 | レビュー待ち件数 | 発散させない（人手レビューの律速を可視化） |
| Tier1 ジャッジ正答率 | judge-accuracy ハーネス | モデル行列で計測、退行検知 |
| フレーク件数 | test:stable での不一致 | 0 維持 |

## 7. リスクと対策

| リスク | 対策 |
|---|---|
| ループが FP 修正のために規則を緩め、FN を作る | must-ask ハードゲート + 構造スイートを毎修正後に実行（P1）。`judge-no-loosen.test.ts` が既にこの方向の退行を監視している |
| 自動ラベルの誤りがランタイム無音許可に波及 | `provably-benign` の自動追加を禁止（P2）。standing-allow カタログ生成はビルド時のため、コーパス差分レビューで必ず可視化される |
| 個別ケースへのパッチワーク化（過学習） | holdout 分割（P5）+ 修正は「規則の一般化」を優先し、コマンド文字列への特判を禁止 |
| LLM 赤チーム生成物の品質ばらつき | 生成物は必ず実分類・実テストを通してから採用。決定的変異エンジン（案C）を主、LLM を従とする |
| コーパス肥大による評価速度低下 | 現状 27→数百件でも corpus 評価は秒単位。1万件超で問題化した時点で並列化を検討（現時点では対策不要） |
| イテレーションレポートの散逸 | `artifacts/quality-loop/` に JSON で蓄積し、`belay quality` の notes に最新イテレーション番号を表示する拡張を検討 |
